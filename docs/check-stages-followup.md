# 영역별 화면 검사와 변경 영향 선택의 2단계 후속 설계를 정의한다.

이 문서는 DEV-259 계획서 v1의 Task 4 산출물이다. 1단계의 단계 실행·서버 결과 보관·재사용 계약을 바탕으로 후속 구현의 경계와 정책을 정한다. 여기 적은 영역 선택·전체 검사 정책은 제안 명세이며 현재 실행 동작을 변경하거나 새 검사를 위임하지 않는다.

## 현재 계약과 구현 경계

- DEV는 승인된 `## 검사`의 정확한 명령과 필수 여부, 사람이 저장한 선택을 실행한다. 선택값 NULL은 전부를 뜻한다. `## 검사 입력`은 해당 명령의 static/functional/browser 단계, 입력, 고정 조건과 재사용 허용을 선언한다.
- 영역 선택과 통과 결과 재사용은 별개다. 영역 선택은 승인된 검사 후보 중 필요한 범위를 정하고, 재사용은 선택된 검사의 서버 성공 결과가 지금도 유효한지 검증한다. 영역이 같다는 사실만으로 재사용하지 않는다.
- DEV 공용 후속 구현은 프로젝트별 영역 계약 검증, 변경 영향 판정, 승인·선택과의 대조, 판정 근거 보관 및 기존 서버 실행 경로 연결을 맡는다. 임의 명령을 만들거나 MCP에 cwd·명령·환경 인자를 추가하지 않는다.
- CH 등 프로젝트의 `scripts/screens.py` 영역 분리, 시나리오·fixture 목록 및 기능 검사 구현은 각 프로젝트의 별도 이슈에서 다룬다. 아래 경로·명령은 계약 예시이며 다른 프로젝트 소스를 확인한 결과가 아니다. 이 Task에서는 다른 프로젝트 수정·이슈 발행을 하지 않는다.

## 영역과 프로젝트별 opt-in

| 영역 | 책임 | 화면 후보 |
| --- | --- | --- |
| account | 계정 메뉴·프로필·멤버십·인증 상태 | Free/Pro 상태와 메뉴 표시 |
| reader | 읽기 화면·읽기 설정·탐색 | 본문과 읽기 조작 |
| studio | 작성·편집·미리보기 | 편집 상태와 저장 흐름 |
| all | 프로젝트가 선언한 전체 화면 시나리오 | 위 영역과 그 밖의 화면 전부 |

영역 이름은 프로젝트가 지원하는 목록으로 검증한다. all은 전체 시나리오 집합이며 단순히 세 영역의 합으로 한정하지 않는다. 공유 메뉴는 account 소유라도 reader·studio에서 사용하면 그 소비 관계를 함께 선언한다.

프로젝트별 승인 계획에서 영역 계약의 버전, 영역별 정확한 실행 명령, 시나리오 목록, 파일 패턴과 공유 컴포넌트의 소비 영역, 입력·조건, 전체 검사 시점을 명시해 opt-in한다. 선언이 없거나 잘못되면 기존 승인 명령을 그대로 실행한다. 자동 선택은 opt-in 뒤에도 승인된 후보 집합 안에서만 작동한다.

프로젝트 실행기는 예를 들어 `python scripts/screens.py --area account`와 `--area all`을 지원할 수 있다. 인자를 생략한 기존 명령은 기존 전체 실행 의미를 보존한다. 미지원 영역은 오류로 종료하고 빈 시나리오를 성공으로 처리하지 않는다. DEV는 명령 이름으로 영역을 추측하거나 기존 명령에 인자를 붙이지 않는다.

## 변경 파일과 공통 컴포넌트 영향

판정 입력은 기준 SHA와 검사 대상 트리 사이의 변경 경로 전체다. 추가·삭제와 이름 변경의 양쪽 경로를 포함하고, 미커밋·임시 검사 입력도 놓치지 않는다. 프로젝트가 승인한 경로 규칙과 소비 관계로 영향을 전이시킨 뒤 영역의 합집합을 구한다.

| 변경 종류 | 기본 판정 | 근거 |
| --- | --- | --- |
| account 전용 코드·시나리오 | account 및 선언된 소비 영역 | 전용 규칙과 소비 관계 |
| reader 또는 studio 전용 코드 | 해당 영역 및 소비 영역 | 영역 소유 경로 |
| 두 영역에 걸친 변경 | 두 영역의 합집합 | 모든 변경 경로를 합산 |
| 공통 CSS·토큰·폰트·레이아웃·공유 shell | all | 전역 배치와 테마 영향 |
| 공통 인증·라우팅·데이터 fixture | 소비 영역 전체, 소비 관계가 불완전하면 all | 화면 상태의 공통 입력 |
| 검사 실행기·영역 매핑·브라우저 설정·의존성 | all | 검사 조건 자체의 변경 |
| 미분류 경로·해석 불가·기준 불명·경로 누락 | all | 축소 근거 없음 |

전용 CSS라도 공유 import가 있으면 소비 관계를 따른다. 문서 전용 변경의 화면 검사 제외도 프로젝트가 명시적으로 승인한 규칙이 있을 때만 허용한다. 일치 규칙이 없다는 이유로 빈 범위를 선택하지 않는다. 규칙 간 충돌이나 소비 관계의 누락·순환으로 범위를 확정하지 못하면 all로 전환한다.

판정 순서는 변경 목록 확정 → 계약 유효성 확인 → 경로 매핑과 소비 관계 전파 → 전체 검사 강제 조건 적용 → 승인 명령·필수·선택 대조 → 실행 또는 재사용 유효성 검증이다. all이 필요하지만 승인된 전체 명령이 없으면 영역 검사를 전체 통과로 대신하지 않고 승인 보완이 필요하다는 보류 사유를 남긴다.

## 계정 메뉴의 8장 기본 후보

계정 메뉴에만 영향이 있다고 증명된 변경은 관련 기능 검사와 다음 화면 8장을 기본 후보로 한다. 기능 검사는 Free/Pro 표시, 메뉴 열기·닫기와 링크·상태 분기를 프로젝트 구현에 맞게 선언한다.

| 테마 | 화면 크기 | 멤버십 | 캡처 수 |
| --- | --- | --- | --- |
| 낮 | PC | Free, Pro | 2 |
| 낮 | 모바일 | Free, Pro | 2 |
| 밤 | PC | Free, Pro | 2 |
| 밤 | 모바일 | Free, Pro | 2 |

각 시나리오는 viewport, fixture 버전, 메뉴 상태와 기대 표시를 고정한다. 공유 메뉴가 다른 화면에서 다르게 배치되면 소비 화면 검사를 추가하는 별도 승인 후보가 필요하며, 8장으로 충족했다고 간주하지 않는다. 공통 CSS·레이아웃 변경이나 영향 불명 시에는 all 정책을 적용한다. 8장은 모든 프로젝트의 고정 의무나 기존 필수 전체 명령의 대체물이 아니다.

## 전체 검사 시점

- 공통 CSS·레이아웃 변경과 영향 판정 불명 시 all을 요구한다.
- opt-in 프로젝트는 최종 병합 후보의 합쳐진 트리에서 all을 요구하는 정책을 승인 계획에 포함한다. Task 브랜치의 영역 검사 통과로 이를 대신하지 않는다. 전체 검사의 정확한 입력·조건이 동일한 서버 결과만 기존 재사용 계약에 따라 인정한다. 항상 새 실행이 필요한 정책이면 해당 명령의 reuse를 금지한다.
- 정기 all 검사는 프로젝트별 주기·담당·명령·실행 조건·비용 한도를 별도로 위임한 뒤 수행한다. 정기 결과는 당시 트리의 결과이며 현재 Task 성공을 자동으로 증명하지 않는다.

이 정책을 구현할 때 현재 병합의 변경 파일 겹침 기반 재검사와 최종 all 의무를 별도로 다룬다. 겹침 없음이 새로 승인된 최종 all 의무를 면제해서는 안 된다. 기존 빌드·health와 언제나 하는 안전 절차도 유지한다. 이 문서만으로 병합 검사나 정기 작업을 추가 실행하지 않는다.

## 기존 필수 검사·선택과의 호환

1. 기존 필수 전체 명령은 정확한 명령 그대로 유지한다. account가 충분해 보여도 자동 축소하거나 선택 해제하지 않는다. 대체하려면 새 계획 판에서 영역별 후보와 전체 실행 조건을 명시하고 사람이 승인해야 한다.
2. 선택 검사는 사람이 해제한 상태를 유지한다. 영역 판정이 필요성을 발견해도 조용히 다시 켜지 않는다. 승인 정책과 해제가 충돌하면 충돌을 표시하고 승인·선택 보완 전에는 해당 요구를 충족했다고 보고하지 않는다.
3. 자동 선택으로 제외할 수 있는 것은 승인된 영향 선택 정책이 조건부 후보로 명시한 검사뿐이다. 단순한 선택 해제와 구별해 판정 사유를 기록하며, 조건부 후보 표현은 후속 계약 확장이 필요하다. 현재 필수/선택 플래그를 조건부 의미로 재해석하지 않는다.
4. 기존 계획에 영역 메타데이터가 없으면 종전 명령과 단계·재사용의 보수적 기본값을 유지한다. 영역 opt-in은 입력 누락·환경 불명 시 재실행하는 1단계 원칙을 완화하지 않는다.
5. 앞 단계 실패로 실행하지 못한 검사는 blocked, 사람의 선택 해제는 not_selected로 남긴다. 영역 정책으로 적용 대상이 아닌 후보는 별도 사유로 구별하며 passed/reused로 위장하지 않는다. 새 상태가 필요하면 후속 계약에서 정의하고 현재 결과 형식에 임의로 추가하지 않는다.

## 결과와 후속 구현의 수용 기준

서버 상세 결과에는 기준·대상 트리, 영역 계약 버전, 변경 경로, 적용 규칙과 소비 관계, 후보·선택 영역, all 전환 사유, 승인 명령과의 대응을 남긴다. 요약에는 실행/재사용/보류와 원 실행, 실제 시간, 캡처 생성·AI 열람·게시판 첨부를 구별한다. 전체 목록은 상세에 두고 대표·실패 이미지만 기존 상한 안에서 제시한다. 캡처 수만으로 절감 시간이나 AI 비용을 확정하지 않는다.

후속 구현 계획은 다음 사례를 임시 검사로 검증하도록 설계한다. 이 문서 Task에서 검사 파일을 추가하거나 실행하지 않는다.

- account 전용 변경은 관련 기능·8장 후보를 선택하고, 소비 영역 변경은 합집합으로 확장한다.
- 공통 CSS, 미분류·삭제·이름 변경, 계약 불명은 all로 전환하며 빈 검사 통과가 발생하지 않는다.
- 필수 전체 명령·NULL=전부·사람의 해제·옛 계획 의미가 보존되고 승인 없는 명령은 실행되지 않는다.
- 최종 합쳐진 트리와 정기 검사의 정책이 적용되며, 필요한 all 명령 부재는 보류로 드러난다.
- 동일 영역이어도 코드·스크립트·fixture·설정·환경 변경은 재사용을 무효화한다. 실제 실행 계수로 실행·재사용·보류를 구별한다.

후속 이슈는 DEV의 공용 계약·선택기와 프로젝트별 실행기 영역 분리를 각각 범위로 삼고, 프로젝트 opt-in은 두 계약의 호환성을 확인한 뒤 승인한다. 운영 재시작·새 외부 유료 호출·정기 실행 등록은 각 후속 작업의 별도 승인 범위다.
